# Idea brief — agora

> 这是**项目级**愿景文档，不是某个特性的 spec。它回答「这个项目整体要做什么、有哪些场景、按什么顺序做」。每个场景的**解决方案**在各自的 `docs/features/<slug>/` 里，不在这里。

## 1. 一句话定位

> **一个可复用的「多方接力协作引擎」：多个参与者围绕一个主题，按可配置的顺序轮流产出一条消息，落到一张所有人可见、有序、可持久化的共享记录上，按可配置的条件停止——角色、顺序、停止、界面全部可插拔。** 先由命令行驱动，未来经同一引擎接 Web 论坛界面。

## 2. 背景与问题

现有 `13_weave` 框架已经提供了循环（Loop）、记忆（Memory）、命名空间隔离与 LLM 适配，demo 也证明了多个人设能并行作答。真正的缺口是：**缺少一条「共享、按序」的协作循环**——多方围绕一个主题、按顺序接力、人人可见、可收敛。这是 brainstorm 需要、demo 没有的东西。

本项目的价值是把这条循环做成**可复用的引擎**，让「头脑风暴」只是它的第一个场景，后续「辩论 / 圆桌 / 面试 / 论坛」都只是同一引擎上的不同配置，而不是各写一套。

## 3. 三层模型（命名对齐，避免混用）

| 层 | 是什么 | 本项目里叫什么 | 状态 |
|---|---|---|---|
| **引擎** | 接力协作内核（有序接力、持久化、恢复、原子能力 + 声明式配置） | `agora`（引擎名 = 仓库名） | 半成品：brainstorm 内已有一份，未抽成通用层 |
| **场景** | 引擎上的一类具体应用（头脑风暴 / 辩论 / 面试…） | `brainstorm` 等，各一个 `docs/features/<slug>/` | brainstorm 已交付 |
| **界面** | 人怎么和场景交互（命令行 / Web 论坛） | `cli`（已有）、`forum`（未来） | cli 已有，forum 未做 |

> **命名**：引擎名 **`agora`**（取自希腊「公共议事广场」，对应多方议事）——即本项目仓库名；场景名 `brainstorm`/`debate` 等；界面名 `forum`。原目录名 `14_forum` 只命了「界面」这一层、易与引擎混用，故正名为 `agora`。三层分清，避免「forum 既是界面又是引擎」。

## 4. 适用场景（引擎上可搭的，brainstorm 是第一个）

| 场景 | 参与者 | 顺序（selector） | 停止（terminator） | 消息语义 | 优先级 |
|---|---|---|---|---|---|
| **头脑风暴** brainstorm | 多个人设 | round_robin | 固定轮 / 收敛 | 想法 | 已交付 |
| **辩论** debate | 正/反 + 裁判 | 交替 | 法官裁决 | 论点 | 候选 |
| **圆桌/多方评审** round-table | 多位评审 | round_robin | 固定 / 主持裁定 | 意见 | 候选 |
| **面试** interview | 面试官 + 候选 | 严格交替 | 固定轮 / 面试官定 | 问答 | 候选 |
| **红蓝对抗** red/blue | 红队 + 蓝队 | 交替 | 判负 / 上限 | 攻防 | 候选 |
| **论坛讨论** forum | 人设 +（未来）真人 | 可插拔 | 手动 / 热度 | 帖子 | 候选（界面层） |
| **观察者角色** observer | 观察者（不发言，总结/评分） | — | — | 评注 | 候选 |

> 每个候选场景在引擎泛化（§7 步骤 2）之后，大多是**纯配置**（模板 + 注入字段 + 选择/停止原子），非新代码；只有需要新「能力」（如查知识库、调工具）时才写新原子。

## 5. 核心能力（固定原子面）

引擎的**功能**是一组收敛的原子，写一次、复用于所有场景：

| 能力 | 原子 | 说明 |
|---|---|---|
| 会话生命周期 | create / run / stop / resume / export | 发起、运行、停止、恢复、导出 |
| 接力编排 | relay() | 选人 → 产出 → 落桌 → 判停 的循环 |
| 共享记录 | StreamStore | append-only、有序、标注参与者、全员可见 |
| 发言产出 | render + llm + parse | 模板 + 上下文 → LLM → 消息 |
| 顺序决策 | round_robin / llm_pick | 谁下一个发言 |
| 停止决策 | fixed_rounds / llm_verdict / manual | 何时结束 |
| 私有记忆 | StateStore（per-participant ns） | 每人私有、他人不可见 |
| 观测 | observers / 事件 | 进度可见，不承载控制流 |
| 持久化/恢复 | StreamStore + resume | 崩溃恢复到中断轮、不重放 |
| 声明式配置 | config schema | YAML 描述场景，零代码切换 |

## 6. 范式：场景 = 能力 × 配置

- **能力**（会重复出现的）：接力、持久化、LLM 调用、模板渲染、输出解析、轮转、判停——写一次。
- **场景**（多变的内容）：谁参与、说什么、按什么顺序、何时停、长什么样——全走配置。
- **边界**：配置只能组合已有原子；新「能力」（调 LLM 之外的 lookup/tool.call/search）= 新原子 = 写代码。能力集合相同的场景之间，切换成本趋近于零。

## 7. 交付顺序与依赖（roadmap 的源）

| # | 步骤（用户能做什么） | 来源 | 依赖 | 状态 |
|---|---|---|---|---|
| 1 | **头脑风暴引擎**——发起一场多角色接力头脑风暴，读讨论记录 | §4 brainstorm | — | building（feature/brainstorm，review CHANGES REQUESTED，8 条 fix-now 待修） |
| 2 | **引擎泛化**——把 §5 的原子抽成 L1 接力层 + 声明式配置，brainstorm 变成其中一个配置 | §3 引擎、§5 | 1 | idea |
| 3 | **论坛界面**——Web 端发起/阅读/停止会话（多角色讨论场） | §3 界面、§4 forum | 2 | idea |
| 4 | **第二个场景（辩论）**——零代码用配置搭出正反辩论 + 法官裁决 | §4 debate | 2 | idea |
| 5 | **观察者角色**——非发言的观察者总结/评分 | §4 observer | 2 | idea |

依赖方向：`1 → 2 → {3, 4, 5}`。步骤 3/4/5 在引擎泛化后彼此**代码区不相交**（界面 / 场景配置 / 新角色），可并行。

## 8. 非目标（本项目不做）

- 不重写/增强 `13_weave` 的 Loop、Memory、LLM 适配——那是依赖。
- 不做通用闲聊 / 无边界对话——引擎始终是「有主题、有顺序、有停止条件」的结构化接力。
- 不让真人以参与者身份**中途插入接力**（人只发起/观察/停止）——真人参与是论坛界面（§7 步骤 3）未来再议的方向，本定位先以 AI 角色接力为准。
