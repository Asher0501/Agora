# Spec — agora

> **Glossary:** [CONTEXT](./CONTEXT.md)
> **Project:** [idea-brief](../../idea-brief.md) —— 本特性是「多方接力协作引擎」**引擎层**的泛化（roadmap 步骤 2）：把 brainstorm 里的内核抽成无语义的 `agora` 接力层。
> **Reference:** `docs/features/brainstorm/_design/atomic-relay.md`（设计草案）、brainstorm 源码（`engine/loop.py`、`weave_adapter/repository.py`、`business/protocols.py`）、brainstorm 的 `spec.md`/`sad.md`/`data-model.md`。

## 1. Context

**我们要解决的**：brainstorm 已经证明了「多角色按序接力 + 共享桌面 + 停止条件 + 扩展点」这套模式可行，但它的内核被 brainstorm 语义绑死——角色、调度、停止条件都写成了 brainstorm 专用的 Python 扩展点，换一个场景（辩论、面试）就得再写一套。目标用户是**场景作者**：想在引擎上搭「头脑风暴 / 辩论 / 面试」这类场景的人。他们要的不是「再写一个引擎」，而是「填一份配置就能跑一个新场景」。

**为什么是现在**：brainstorm 是第一步（已交付），它是「多方接力协作引擎」的第一个场景。idea-brief 已经把「辩论 / 圆桌 / 面试 / 论坛 / 观察者」列为候选场景，且 roadmap 步骤 3/4/5 都依赖「引擎先被抽成通用层」。现在是把内核抽象出来的时机。

**已承诺的方案**：引擎提供一组收敛的**原子**（产出 / 选人 / 判停 / 存储 / 摘要），场景作者从这份**闭集菜单**里组合出场景——能力集合相同的场景 = 一份**声明式配置**（零引擎代码改动）。菜单之外、确需自定义代码的能力，走一个明确隔离的**扩展区**接口（受控逃生门，不混入标准菜单、接口风格可自定义）。**配置校验是一等能力**：非法配置在加载时被拒绝并给出清晰原因，而不是运行时才崩。**配置 = YAML 数据文件**（schema 沿用 `docs/features/brainstorm/_design/atomic-relay.md` §2；`topic`/`stance` 等运行时值由每场会话注入，不写死进配置）；加载校验器认可的「已知能力」= **闭集菜单 ∪ 已注册的扩展能力**（扩展先注册、后加载配置，未注册即拒）。**下沉原则**：引擎只强制「业务无关」的机制（防失控空转的条数上限、每个 turn 恰好一次、跨会话隔离）；「业务可被 prompt 解决」的行为（如防止选人者反复点中同一角色）留给场景作者在 prompt 里约束，不写成引擎结构校验。

**追溯**：现状参考 brainstorm 的回合循环（`engine/loop.py`）、存储（`weave_adapter/repository.py`）、四扩展协议（`business/protocols.py`），以及设计草案 `docs/features/brainstorm/_design/atomic-relay.md`。本特性是一次破坏性重构——旧的四扩展协议被「原子 + 声明式配置」取代。

## 2. Goals

- 让「能力集合相同的新场景」从写一套引擎代码，变成填一份声明式配置（**零引擎代码改动**）。
- 让引擎与场景语义解耦：内核只做「按序接力 + 共享转录 + 判停 + 持久化恢复」，不懂任何具体场景。
- 让配置错误在**加载时**就被发现并给出可读原因，而不是跑到一半才崩。
- 让 brainstorm 迁移到新引擎上作为第一个场景，实证「零代码扩展」成立。
- 让菜单之外的能力有一条受控出路（扩展区），不因此污染标准菜单的「零代码 + 严格校验」。

## 3. Non-goals

- 不做「开放插件 ABI」——本轮不建立「场景自带给选人/产出/判停钩子」的版本化扩展契约；自定义能力走扩展区，但扩展区本轮**不承诺稳定/版本化**。
- 不做「会话结构 / 阶段」声明层——多阶段场景（如辩论的立论/自由辩/裁决）留到 debate 实际需要时再设计，不提前造结构语言。
- 不重写/增强 weave 的 Loop、Memory、LLM 适配——那是依赖。
- 不让真人以参与者身份中途插入接力——人只发起/观察/停止。
- 不做「观察者角色」（会话进行中的总结/评分型只读角色）——那是 roadmap 步骤 5；本轮引擎保留可观测的进度事件与「会话终止时的一次性总结」，但不实现观察者角色的进行中产出。
- 不迁移已存在的旧 brainstorm 会话数据——破坏性变更被允许；旧会话不保证能恢复到新引擎。

## 4. User stories

### US-01: 场景作者用纯配置定义场景

**As a** 场景作者
**I want** 用一份声明式配置描述一个场景的角色、选人、判停与产出
**So that** 不用写任何引擎代码就能让场景跑起来

### US-02: 发起人运行一场会话

**As a** 发起人
**I want** 给定一个场景与运行时值，启动并跑完一场会话
**So that** 得到一份有序的共享转录、一份会话总结（任意终止路径），以及裁判收敛时的一份结论

### US-03: 参与者按序接力发言

**As a** 角色
**I want** 轮到自己时，基于主题与历史发言产出一条发言
**So that** 讨论持续推进而非各自独立作答

### US-04: 选人者决定发言顺序

**As a** 选人者
**I want** 在每次发言后决定下一位发言者
**So that** 讨论有方向

### US-05: 裁判判定收敛

**As a** 裁判
**I want** 结合共享转录判定讨论是否已收敛
**So that** 讨论在恰当的时点收敛，并产出一份结论（裁判的收敛判断）

### US-06: 角色维持跨轮连续性

**As a** 角色
**I want** 把共享转录的摘要存进自己的私有状态，并在后续发言中引用它
**So that** 裁判等角色能跨轮累积判断，而非每轮从零开始

### US-07: 场景作者在加载时发现配置错误

**As a** 场景作者
**I want** 非法配置在加载时被拒绝并说明原因
**So that** 不会等到运行时才发现写错

### US-08: 扩展者经扩展区接入自定义能力

**As a** 扩展者
**I want** 在扩展区写自定义代码接入引擎
**So that** 菜单之外的能力也能实现，且不污染标准菜单

### US-09: 发起人中断后恢复会话

**As a** 发起人
**I want** 会话中断后恢复到中断的那一轮、已落桌的发言不重放
**So that** 讨论不因一次崩溃而丢失

## 5. Acceptance criteria

### AC-01 (US-01) — happy path

**Given** 场景作者定义了一个与头脑风暴能力集合相同的场景（一组角色、一种选人方式、一种判停方式，及通用的条数上限兜底）
**When** 场景作者用声明式配置表达该场景并运行
**Then** 场景跑通，且引擎代码零改动

### AC-02 (US-02) — happy path

**Given** 场景作者已定义好一个场景
**When** 发起人提供运行时值并启动会话
**Then** 系统创建会话、记录场景与运行时值，并确认会话已开始

### AC-02b (US-02) — error

**Given** 发起人提供的运行时值非法（如缺主题）或引用了不存在的场景
**When** 发起人尝试启动会话
**Then** 系统拒绝启动，并说明原因

### AC-03 (US-01) — error

**Given** 场景作者提交的配置引用了「闭集菜单与已注册扩展能力中都不存在」的选人或判停方式
**When** 系统加载该配置
**Then** 系统拒绝加载，并说明这个选人/判停方式不受支持

### AC-04 (US-07) — error

**Given** 场景作者提交的配置里，某个角色缺少产出所需的描述
**When** 系统加载该配置
**Then** 系统拒绝加载，并说明哪个角色缺什么

### AC-05 (US-03) — happy path

**Given** 一个进行中的会话，共享桌面上已有主题与若干历史发言
**When** 轮到某位角色发言
**Then** 该角色产出一条承接主题与历史的发言，系统将其记为下一条按序发言并标注发言者

### AC-06 (US-03) — domain invariant

**Given** 一个接力 turn 已由某位角色产出了一条发言
**When** 系统在同一 turn 内再次尝试产出发言
**Then** 系统阻止，不产生第二条（每个 turn 恰好一条发言）

> 注：「选人者反复点中同一角色」属业务行为，由场景作者在选人 prompt 里约束，不构成引擎结构校验（同 §8 自选自判哲学）。

### AC-07 (US-04) — happy path

**Given** 场景配置了「由某角色选下一位发言者」
**When** 某位角色完成一次发言
**Then** 系统在路由时点请选人者选定下一位发言者

### AC-07b (US-04) — domain invariant

**Given** 选人者选定的下一位发言者不在角色名单内
**When** 系统解析该选择
**Then** 系统优先重试让选人者重新选；重试仍无效则回退到角色名单顺序选取下一位，并把每次无效选择记录为观测事件

### AC-08 (US-05) — happy path

**Given** 场景配置了「由某角色判定收敛」
**When** 裁判结合共享转录宣告已收敛
**Then** 系统结束会话，产出一份会话总结，并附上裁判的结论（收敛判断）

### AC-09 (US-05) — happy path

**Given** 场景以「按固定条数停止」为判停方式（每个场景另有条数上限兜底）
**When** 在下一条发言产出前，讨论已达配置的条数
**Then** 系统自动结束会话并产出一份会话总结（不额外多产出一条发言）

### AC-10b (US-05) — domain invariant

**Given** 场景配置了「由裁判判定收敛」，但裁判始终未宣告收敛
**When** 讨论达到配置的条数上限
**Then** 系统强制结束会话，产出一份会话总结并标注「未收敛」

### AC-11 (US-02) — happy path

**Given** 会话进行中，且场景配置了「手动停止」
**When** 发起人发出停止指令
**Then** 系统取消当前正在进行的生成（该发言不落桌），结束会话并产出一份会话总结、标注「手动停止」

### AC-12 (US-06) — happy path

**Given** 场景为角色配置了「把共享转录摘要存入私有状态」
**When** 角色轮到时
**Then** 该角色能读到自己的摘要，并据此产出发言（跨轮连续性成立）

### AC-13 (US-07) — cross-context

**Given** 场景配置里，裁判的产出格式与「判定收敛」所需不符（例如裁判被配置为纯文本产出，却要它宣告收敛）
**When** 系统加载该配置
**Then** 系统拒绝加载，并说明这个不匹配

### AC-14 (US-08) — happy path

**Given** 扩展者在扩展区接入了一个自定义能力
**When** 该能力被一个场景使用
**Then** 该能力生效，且标准菜单与引擎其余部分不受影响

### AC-15 (US-09) — happy path

**Given** 一场会话在运行中因故障中断，且已有若干发言落桌
**When** 发起人恢复该会话
**Then** 系统恢复到中断的那一轮，已落桌的发言不重放、不丢失，各角色的私有状态一并恢复；崩溃前未落桌的在途发言丢弃、该轮重试

### AC-15b (US-09) — error

**Given** 发起人尝试恢复一个不存在或损坏的会话
**When** 系统处理该恢复请求
**Then** 系统拒绝恢复并说明原因

### AC-16 (US-03) — authorization

**Given** 一个角色属于会话 A
**When** 该角色尝试读取会话 B 的共享转录或另一角色的私有状态
**Then** 系统按会话/角色隔离，会话 B 的内容与别的角色的私有状态不向该角色暴露

### AC-17 (US-02) — authorization

**Given** 一位发起人名下有自己的会话
**When** 该发起人尝试读取另一场会话的共享转录或任一角色的私有状态
**Then** 系统按发起人命名空间隔离，他人的会话内容与角色私有状态不向该发起人暴露

### AC-18 (US-02) — progress events

**Given** 一场会话在进行中，引擎向外发送可观测的进度事件
**When** 任一发起人订阅进度事件
**Then** 事件只携带本会话（本命名空间）的内容，不含他会话的转录摘录或私有状态

## 6. Non-functional requirements

| Aspect | Target | Measurement |
|---|---|---|
| 每轮编排开销（不含生成）延迟 p95 | ≤ 100 ms | 本地插桩 |
| 读取完整共享转录延迟 p95 | ≤ 50 ms | 本地插桩 |
| 并发会话数 | ≥ 5 个会话数据隔离（AC-16/17）且并发下 p95 延迟不劣化（劣化倍数 design 定） | 并发冒烟测试（隔离断言 + 并发 p95 对比） |
| 会话可靠性（可用性） | 按月窗口，已开始的会话 ≥ 99.9% 不被意外中断（仅计崩溃 / 生成失败 / 超时 / 断连；排除手动停止 / 封顶 / 裁判收敛） | 耐久测试（按上述排除项口径统计） |
| 一致性 / 耐久 | 每场会话 0 条丢失或重复发言 | 追加顺序不变量测试 |
| 配置加载正确性 | 非法配置 100% 在加载时被拒绝 | 覆盖全部已知非法类别的校验测试 |

## 6.1 Security / privacy

- **Data classification:** internal —— 讨论记录可能包含未定稿的产品/技术推理，不宜对外公开。
- **Personal data touched:** 无 —— 角色均为虚构，不收集真实个人信息。
- **AuthZ/AuthN impact:** 会话之间、角色之间按命名空间隔离；角色只能读本会话的共享转录与本角色的私有状态。
- **Abuse cases:**
  - 自选自判（同一角色既在发言名单、又被配为选人者/裁判 → 自我收敛的「作弊」转录）：引擎无语义、不阻止此配置——作为已知风险记录，由场景作者负责；是否加结构性校验留待设计（见 §8）。
  - 主题注入：恶意主题诱导角色泄露系统提示或其它会话内容 → 主题按不可信数据处理。
  - 摘要失真：摘要丢弃关键信息导致裁判误判收敛 → 记录为已知风险，摘要原子需可观测。
  - 失控空转：主题导致角色无限产出 → 判停方式与条数上限兜底。
- **Security review:** Required —— 新的多角色生成边界 + 配置成为「准代码」后的注入面。扩展区代码的信任边界（是否同进程、能否跨命名空间读）见 §8。

## 7. Metrics / KPIs

- **零代码扩展** — baseline: 0 个纯配置场景，target: brainstorm 迁移为纯配置后，能力集合相同的新场景 = 0 处引擎代码改动（本特性内实证）。
- **配置即校验** — baseline: 非法配置在运行时才崩，target: 非法配置在加载时 100% 被拒绝并给出可读原因。
- **会话完整性** — baseline: 0（新引擎），target: 100% 会话零丢失、零重复发言。
- **单会话成本** — baseline: TBD，target: 一场 N 条发言会话的生成成本在预算内（记录每场 token 用量）。

## 8. Open questions

- [ ] 引擎是否要加「裁判/选人者不得同时在发言名单」的结构性校验，还是留给场景作者负责（无语义）？Default now: 留给场景作者，仅文档化风险。— owner: Tech Lead, due: before sdd:design
- [ ] 选人与判停拆成两个原子后，收敛判断的时序与成本（裁判可能被调用两次、收敛前多一条发言）如何优化？Default now: 接受拆分，设计阶段评估是否让判停先于产出。— owner: Tech Lead, due: before sdd:design
- [ ] resume 时，会话按「创建时快照的配置」还是「恢复时实时读取的配置」运行？Default now: 快照（创建时定格），避免崩溃后改配置导致半程规则变化。— owner: Tech Lead, due: before sdd:design
- [ ] 裁判产出解析失败（不含预期格式）时如何回退、是否发观测事件？Default now: 确定性回退（视为不收敛）+ 记录观测事件。— owner: Tech Lead, due: before sdd:design
- [ ] 扩展区接口本轮是否承诺稳定/版本化？Default now: 不承诺，作为「内部逃生门」交付。— owner: Tech Lead, due: before sdd:design
- [ ] 选人无效时的重试次数上限？Default now: 1 次。— owner: Tech Lead, due: before sdd:design
- [ ] 扩展区代码的信任边界：扩展区代码与引擎是否同进程、能否跨命名空间读取其它会话/角色私有状态？Default now: 同进程、视为受信代码，但读范围以 AC-16/17 为界（不跨命名空间）。— owner: Security Lead, due: before sdd:design
- [ ] 并发 relay 同一 run 的重复产出防护：AC-06 的 `TURN_ALREADY_PRODUCED` 守卫目前只在显式 seq 分支生效，relay 走 `max+1` 自动序号，两个并发 relay 同一 run 会重复产出（触及「0 重复发言」不变量 / AC-15 resume 竞态窗口）。Default now: 暂不修（单进程单会话单任务模型下不会发生；并发 resume 竞态非本轮承诺面，见 review r3 finding 3）。— owner: Tech Lead, due: 多进程/服务化迭代
